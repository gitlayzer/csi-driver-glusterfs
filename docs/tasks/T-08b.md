## 背景（必读）
T-09 真实集群验收发现 T-08 的 target 刷新方式是错的（docs/decisions.md D-19 备注）：
- 业务容器声明 `mountPropagation: HostToContainer` 时，它的 volumeMount 是宿主机 target 挂载的 rslave 副本。
  宿主机 **lazy-unmount（detach）target 再重新 bind**，新挂载**不会**传播进容器：容器里的那份副本已经和宿主机上被卸掉的挂载一起脱离了，
  容器继续看到 `ENOTCONN`，直到存活探针重启容器。
- 宿主机**不卸载**，直接在 target 上**叠加**一层新的 bind（挂在失效挂载之上），新层会作为子挂载传播进容器，容器里的 I/O 在 1 秒内恢复，
  容器不重启。对一个 stat 返回 `ENOTCONN` 的失效 FUSE 挂载点做 `mount --bind` 是可以成功的（已在节点上验证）。

另外，node-2 上启动时的那一轮扫描与 FUSE 进程退出存在竞态，失效挂载被判为健康，直到下一轮（60s 后）才恢复。用户决定把默认间隔改为 10s（D-20）。

后果：插件每重启一次，已发布卷的 target 上就多一层挂载（下面是失效层）。这些层在 NodeUnpublish 时一并卸掉，所以卸载要循环到 target 不再是挂载点。

## 设计

### `pkg/mounter`
`Mounter` 接口新增（放在 `BindMount` 之后）：
```go
// StackBindMount bind-mounts source on top of whatever is mounted at target,
// read only if readOnly is set. Unlike BindMount it does not look at the
// current mount and does not refuse a corrupted one: the new mount hides the
// old one, and, unlike an unmount followed by a bind mount, it propagates into
// containers that see target through a HostToContainer (rslave) volume mount.
// Every call adds a layer, so callers use it only on a corrupted target.
StackBindMount(ctx context.Context, source, target string, readOnly bool) error
```
`(*mounter).StackBindMount`：
1. `ctx.Err()`；`validatePath("source", source)`、`validatePath("target", target)`，失败原样返回（`ErrInvalidSpec`）。
2. `os.Lstat(target)`：`fs.ErrNotExist` → `fmt.Errorf("target %q does not exist: %w", target, err)`；`mount.IsCorruptedMnt(err)` → 继续（这正是要处理的情况）；
   其它错误 → `fmt.Errorf("stat target %q: %w", target, err)`；成功 → 继续。
3. 与 `BindMount` 相同的选项：`["bind"]`，`readOnly` 时追加 `"ro"`；`m.inner.Mount(source, target, "", options)`，
   失败 → `fmt.Errorf("stack bind mount %q at %q: %w", source, target, err)`。
4. 成功 `klog.V(2).InfoS("stacked a bind mount", "source", source, "target", target, "options", options)`。
把选项构造提成一个小函数（例如 `bindOptions(readOnly bool) []string`）供两处共用，不要复制。

`unmount(ctx, target, removeDir)` 改为循环卸载多层：
- 新常量 `maxUnmountLayers = 64`，注释说明为什么会有多层（恢复器每次叠加一层，见 D-19）以及上限是为了不在卸载没有进展时死循环。
- 循环最多 `maxUnmountLayers` 次：每次先 `ctx.Err()`；然后与现在相同的 `IsMountPoint` 分支：
  不存在 → 结束循环；`ErrCorruptedMount` → `inner.Unmount` 一次，继续下一轮；其它错误 → 返回；mounted → `inner.Unmount` 一次，继续下一轮；
  不是挂载点 → 结束循环。
- 跑满 `maxUnmountLayers` 次仍未结束 → `fmt.Errorf("target %q is still a mount point after %d unmounts", target, maxUnmountLayers)`，**不删目录**。
- 日志：每卸一层 `klog.V(2)`（保留现有的两条消息），结束时若卸了不止一层再 `klog.V(2).InfoS("unmounted stacked mounts", "target", target, "layers", n)`。
- 结束循环后才按 `removeDir` 删除目录（逻辑不变）。`Unmount` 与 `Cleanup` 都走这个循环。

### `pkg/driver/recovery.go`
`refreshTarget` 处理 `Corrupted` 时**不再调用 `Detach`**，改为 `s.mounter.StackBindMount(ctx, rec.StagingTargetPath, target.Path, target.ReadOnly)`；
失败 → 返回 `fmt.Errorf("stack a bind mount on the corrupted target %q: %w", ...)`，target 留在待刷新列表（与现在的失败处理相同）。
成功日志改为 `"stacked a fresh bind mount on a target"`。更新 `refreshTargets`/`refreshTarget` 的注释（"detaches and binds again" → 叠加），
并写清楚为什么不能 detach（不会传播进 HostToContainer 容器）。其余步骤（锁、状态判断、记录保存、staging 的 Detach）**不变**；
staging 仍然 detach 后重挂：容器从不直接挂 staging。

NodeStage 的损坏 staging 自愈复用 `refreshTargets`，自动获得同样的行为，无需另改。

### `pkg/driver/node.go`
`bindMount`（NodePublish 遇到损坏的 target）：`BindMount` 返回 `ErrCorruptedMount` 时，不再 `Unmount` + `BindMount`，
改为 `StackBindMount(ctx, staging, target, readOnly)`；日志改为 `"target mount is corrupted, stacking a fresh bind mount"`；
更新函数注释，理由同上。其它代码不动。

### `cmd/glusterfs-csi/main.go` 与部署清单
- `DefaultRecoveryInterval = 10 * time.Second`，更新常量与 flag 帮助文本中的数值（如果写了数值）。
- `deploy/kustomize/base/node-daemonset.yaml`：`--recovery-interval=60s` → `--recovery-interval=10s`，其它行不动。

## 测试（表驱动，断言行为）
1. `TestStackBindMount`（`mounter_test.go`，`FakeMounter`）：
   - 健康目录 → inner 收到一次 Mount，选项 `["bind"]`；`readOnly` → `["bind","ro"]`（断言 FakeMounter 的 log/MountPoints 的 Opts）；
   - target 已经是挂载点 → **仍然**再挂一层（MountPoints 中该路径出现两次）；
   - target 不存在 → 错误满足 `errors.Is(err, fs.ErrNotExist)`，没有 Mount；
   - 相对路径 / 含 `..` 的 source 或 target → `ErrInvalidSpec`，没有 Mount；
   - ctx 已取消 → 返回 ctx 错误，没有 Mount；
   - inner.Mount 失败 → 错误包装原错误。
   - 损坏的 target（`os.Lstat` 返回 ENOTCONN）在 FakeMounter 中无法构造：把 lstat 做成 `mounter` 的可注入字段（如 `lstat func(string) (fs.FileInfo, error)`，
     `New` 设为 `os.Lstat`），测试注入返回 `&os.PathError{Err: syscall.ENOTCONN}` → 继续并 Mount；注入其它错误（如 `EACCES`）→ 返回错误、没有 Mount。
2. `TestUnmountLayers`：需要一个按内核语义工作的 inner：**每次 `Unmount` 只移除该路径最后一个（最上层）条目**。FakeMounter 一次会移除同路径的全部条目，
   所以在测试里写一个包装类型（嵌入 `*mount.FakeMounter`，覆盖 `Unmount`，并支持"第 k 层是损坏的"——例如该层成为最上层时让 `IsMountPoint` 返回 ENOTCONN）。用例：
   - 三层健康 bind，`Cleanup` → 恰好 3 次 Unmount，目录被删除；
   - 上层健康、下层损坏（恢复器留下的典型形态），`Cleanup` → 2 次 Unmount，目录被删除；`Unmount` → 2 次 Unmount，目录保留；
   - 只有一层（现有行为）→ 1 次 Unmount；
   - inner 的 Unmount 返回成功但不移除任何东西 → 恰好 `maxUnmountLayers` 次 Unmount 后返回错误，目录保留，**不会挂死**；
   - 第二层 Unmount 失败 → 返回错误，目录保留；
   - 循环中途 ctx 被取消（在包装类型的 Unmount 里调用 cancel）→ 返回 ctx 错误，目录保留。
   现有 Unmount/Cleanup 用例必须继续通过。
3. `stack_linux_test.go`（`//go:build linux`，非 root 时 `t.Skip`）：用真实 `mount.New("")` 构造的 mounter，在 `t.TempDir()` 中挂一个 tmpfs 作为 source，
   target 先 bind 一次，再 `StackBindMount(ro=true)` 一次 → `/proc/self/mountinfo` 中 target 出现两条且最后一条含 `ro`；在 target 写文件失败（只读层在上）；
   `Cleanup(target)` → target 目录不存在，mountinfo 中不再有 target；结束时清理 tmpfs。
4. `node_test.go` 的 fakeMounter 新增 `StackBindMount`：记入有序调用日志（格式与现有 bind 一致，如 `"stack:/s->/t:ro"`），可注入错误，成功时把该路径状态设为 Mounted。
5. `TestRecoverVolume` 更新：所有刷新 target 的用例，调用日志中**不得**出现 `detach:<target>`，刷新调用是 `stack:` 而不是 `bind:`，ro 标志按记录传递；
   staging 仍然是 `bindTargets → (保存) → detach staging → mount`；"StackBindMount 失败 → partial，target 留在记录中" 替换原来的 BindMount 失败用例。
6. NodeStage 自愈用例（node_test.go 中已有的损坏 staging 自愈测试）：断言 target 通过 `stack:` 刷新且没有 `detach:<target>`。
7. NodePublish：target 损坏时 → 调用 `stack:` 且没有 `unmount:<target>`，返回成功；`StackBindMount` 失败 → `Internal`。
8. `main_test.go`：默认值断言改为 10s。
