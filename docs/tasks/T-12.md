## 背景（必读）
T-11 实现了 subdir 卷的 CreateVolume / DeleteVolume，controller 模式的二进制会把父卷 FUSE 挂载到 `--controller-mount-dir` 下（D-24）。
本任务把 controller 部署进集群：一个 Deployment 里放驱动（`--mode=controller`）、csi-provisioner 与 livenessprobe 三个容器，
加上 provisioner 需要的 RBAC，以及一个动态卷示例。相关决策（docs/decisions.md）：
- **D-28**：2 副本 + provisioner 选主；hostNetwork + `ClusterFirstWithHostNet`；端口 29652（驱动 healthz）、29653（provisioner）；
  父卷挂载点用 emptyDir；驱动容器特权；provisioner `--timeout=60s`；RBAC 规则照搬上游 v6.4.0，Role 只给 leases。
- **D-29**：示例 StorageClass `onDelete: archive`、`reclaimPolicy: Delete`、`Immediate`、`allowVolumeExpansion: false`；示例 Pod 以 UID 1000 运行。
- **D-21**：node 插件用 hostNetwork 解析 Gluster 主机名，controller 同理。
- 先读现有的 `deploy/kustomize/base/node-daemonset.yaml`：controller 的驱动容器与 liveness-probe 容器的写法（探针、端口、注释风格）
  与它保持一致；示例 Deployment 的写入脚本照抄 `examples/static/deployment.yaml`。

controller 模式下用到的二进制 flag（`cmd/glusterfs-csi/main.go`）：`--mode`、`--endpoint`、`--config`、`--controller-mount-dir`
（controller 模式必填，默认 `/var/lib/glusterfs-csi/controller`）、`--mount-log-dir`，以及 klog 的 `--v`。controller 模式不需要
`--nodeid`、`--state-dir`、`--recovery-interval`，**不要传**。

## 设计

约定与 T-09 相同：所有资源带标签 `app.kubernetes.io/name: glusterfs-csi` 与 `app.kubernetes.io/part-of: glusterfs-csi`（示例资源除外）；
2 空格缩进；每个文件一个资源，文件头一行注释说明用途；不用 `commonLabels`；注释解释“为什么”。
资源名统一用 `glusterfs-csi-` 前缀，集群级资源（ClusterRole / ClusterRoleBinding）也一样，以免与其它驱动冲突。

### `deploy/kustomize/base/kustomization.yaml`
`resources` 依次为：`namespace.yaml`、`csidriver.yaml`、`serviceaccount.yaml`、`node-daemonset.yaml`、`controller-serviceaccount.yaml`、
`controller-clusterrole.yaml`、`controller-clusterrolebinding.yaml`、`controller-role.yaml`、`controller-rolebinding.yaml`、
`controller-deployment.yaml`。文件头第一行改为说明 base 含 node DaemonSet 与 controller Deployment 及其 RBAC；
关于 ConfigMap 的注释改为 node DaemonSet 与 controller Deployment **都**引用 `glusterfs-csi-config`。其余不变。

### `controller-serviceaccount.yaml`
ServiceAccount `glusterfs-csi-controller`。**不写** `automountServiceAccountToken`（保持默认挂载）；注释说明 csi-provisioner 要用 token 访问 API。

### `controller-clusterrole.yaml`
`rbac.authorization.k8s.io/v1` ClusterRole `glusterfs-csi-provisioner`，规则逐条照搬上游 external-provisioner v6.4.0
`deploy/kubernetes/rbac.yaml`（文件头注释写明来源与版本，升级 sidecar 时对照）：

| apiGroups | resources | verbs |
|---|---|---|
| `""` | `persistentvolumes` | get, list, watch, create, patch, delete |
| `""` | `persistentvolumeclaims` | get, list, watch, update |
| `storage.k8s.io` | `storageclasses` | get, list, watch |
| `""` | `events` | list, watch, create, update, patch |
| `snapshot.storage.k8s.io` | `volumesnapshots` | get, list, watch, update |
| `snapshot.storage.k8s.io` | `volumesnapshotcontents` | get, list |
| `storage.k8s.io` | `csinodes` | get, list, watch |
| `""` | `nodes` | get, list, watch |
| `storage.k8s.io` | `volumeattachments` | get, list, watch |

不加 `secrets`（M2 没有 provisioner secret；M3 引入 SSH executor 时再加）。

### `controller-clusterrolebinding.yaml`
ClusterRoleBinding `glusterfs-csi-provisioner`：`roleRef` → ClusterRole `glusterfs-csi-provisioner`；
`subjects: [{kind: ServiceAccount, name: glusterfs-csi-controller, namespace: glusterfs-csi}]`（namespace 显式写出）。

### `controller-role.yaml`
Role `glusterfs-csi-provisioner-cfg`：只有一条规则 `coordination.k8s.io` / `leases` / get, watch, list, delete, update, create。
注释说明：上游 Role 里的 `csistoragecapacities`、`pods`、`replicasets` 只在 `--enable-capacity` 时需要，M3 实现 `GET_CAPACITY` 前不授予。

### `controller-rolebinding.yaml`
RoleBinding `glusterfs-csi-provisioner-cfg`：`roleRef` → Role `glusterfs-csi-provisioner-cfg`；subjects 同上（namespace 显式写出）。

### `controller-deployment.yaml`
`apps/v1` Deployment `glusterfs-csi-controller`
- 标签：`app.kubernetes.io/name: glusterfs-csi`、`app.kubernetes.io/part-of: glusterfs-csi`、`app.kubernetes.io/component: controller`；
  selector 只用 name 与 component；Pod 模板带全部三个。
- `replicas: 2`；`strategy: {type: RollingUpdate, rollingUpdate: {maxSurge: 0, maxUnavailable: 1}}`。注释说明：只有持有 Lease 的
  provisioner 发 RPC，备用副本不挂载父卷；hostNetwork Pod 的端口就是宿主机端口，两副本不会落到同一节点，`maxSurge: 0` 让 2～3 节点的集群
  也能滚动（先删一个旧 Pod 再起新的）。
- Pod：`serviceAccountName: glusterfs-csi-controller`、`hostNetwork: true`、`dnsPolicy: ClusterFirstWithHostNet`（注释引用 D-21/D-28：
  controller 挂载父卷，要像 node 插件一样用节点 `/etc/hosts` 解析 Gluster 主机名）、`priorityClassName: system-cluster-critical`、
  `nodeSelector: {kubernetes.io/os: linux}`；`affinity.podAntiAffinity.preferredDuringSchedulingIgnoredDuringExecution`：
  `weight: 100`、`podAffinityTerm {topologyKey: kubernetes.io/hostname, labelSelector.matchLabels: {name, component: controller}}`。
  不加 tolerations。
- 容器 1 `glusterfs-csi`：
  - `image: ghcr.io/gitlayzer/glusterfs-csi:main`，`imagePullPolicy: IfNotPresent`
  - `args`（逐项写全，顺序固定，`--v=2` 必须是第 6 项即下标 5，测试 overlay 会按下标 patch）：
    `--mode=controller`、`--endpoint=unix:///csi/csi.sock`、`--config=/etc/glusterfs-csi/config.json`、
    `--controller-mount-dir=/var/lib/glusterfs-csi/controller`、`--mount-log-dir=/var/log/glusterfs/csi`、`--v=2`
  - `securityContext: {privileged: true}`，注释：FUSE 挂载父卷需要 `/dev/fuse` 与 mount 系统调用。
  - `ports: [{name: healthz, containerPort: 29652, protocol: TCP}]`，注释：29651 被同节点的 node 插件占用。
  - `livenessProbe`：与 node DaemonSet 相同（`httpGet /healthz port healthz`，10/20/10/5）。
  - `resources`：只有 `requests {cpu: 20m, memory: 64Mi}`，不设 limits；注释：父卷的 FUSE 进程在此容器内，OOM 会中断进行中的建删卷。
  - `volumeMounts`：`socket-dir` → `/csi`；`parent-mounts` → `/var/lib/glusterfs-csi/controller`；`config` → `/etc/glusterfs-csi`
    （`readOnly: true`）；`mount-log` → `/var/log/glusterfs/csi`。**不设** `mountPropagation`（父卷挂载只给本容器用，注释说明）。
- 容器 2 `csi-provisioner`：
  - `image: registry.k8s.io/sig-storage/csi-provisioner:v6.4.0`
  - `args`：`--v=2`、`--csi-address=/csi/csi.sock`、`--leader-election`、`--leader-election-namespace=$(NAMESPACE)`、`--timeout=60s`、
    `--http-endpoint=:29653`。注释说明 `--timeout`：第一次 CreateVolume 要挂载父卷，默认 15s 偏紧；超时的调用会被重试，驱动是幂等的。
    **不加** `--extra-create-metadata`、`--enable-capacity`、`--feature-gates`。
  - `env`：`NAMESPACE` 取 `fieldRef: metadata.namespace`
  - `ports: [{name: provisioner, containerPort: 29653, protocol: TCP}]`
  - `livenessProbe`：`httpGet {path: /healthz/leader-election, port: provisioner}`、`initialDelaySeconds: 10`、`periodSeconds: 20`、
    `timeoutSeconds: 10`、`failureThreshold: 3`；注释：上游建议，leader 连不上 API server 续约时重启它，让另一个副本接手。
  - `resources`：`requests {cpu: 10m, memory: 32Mi}`、`limits {memory: 256Mi}`（PV/PVC informer 随集群规模增长）
  - `volumeMounts`：`socket-dir` → `/csi`
- 容器 3 `liveness-probe`：与 node DaemonSet 的同名容器相同，只把 `--http-endpoint` 改为 `:29652`。
- `volumes`：`socket-dir` emptyDir；`parent-mounts` emptyDir（注释：Pod 退出时 FUSE 进程随容器结束，挂载不需要留存）；
  `config` configMap `glusterfs-csi-config`（与 DaemonSet 相同：不加 optional / items，不用 subPath）；`mount-log` emptyDir。

### `deploy/kustomize/examples/dynamic`
示例资源标签用 `app.kubernetes.io/name: rwx-writer`（StorageClass、PVC 可不加）。
- `kustomization.yaml`：`namespace: glusterfs-csi-dynamic-example`；resources 为 namespace、storageclass、pvc、deployment。
- `namespace.yaml`：Namespace `glusterfs-csi-dynamic-example`。
- `storageclass.yaml`：`storage.k8s.io/v1` StorageClass `glusterfs-subdir`：`provisioner: glusterfs.csi.io`；
  `parameters: {clusterID: prod, provisioningMode: subdir, parentVolume: csi-parent, onDelete: archive}`；`reclaimPolicy: Delete`；
  `volumeBindingMode: Immediate`；`allowVolumeExpansion: false`。注释：clusterID 必须出现在 ConfigMap；父卷由管理员预建并启动；
  archive 把删除的卷移到父卷 `.glusterfs-csi/archive/`（D-26），需要定期清理；`delete` / `retain` 的含义；扩容在 M3 实现，届时改为 true；
  参数拼错会让创建失败（D-22）。
- `pvc.yaml`：PVC `dynamic-data`：`accessModes: [ReadWriteMany]`、`storageClassName: glusterfs-subdir`、`resources.requests.storage: 5Gi`。
- `deployment.yaml`：Deployment `rwx-writer`，结构与 `examples/static/deployment.yaml` 相同（3 副本、topologySpreadConstraints、
  同一写入脚本、HostToContainer、livenessProbe、resources、busybox 1.37.0），差异：
  - 卷 `data` 引用 PVC `dynamic-data`；
  - Pod `securityContext: {runAsNonRoot: true, runAsUser: 1000, runAsGroup: 1000, seccompProfile: {type: RuntimeDefault}}`；
  - 容器 `securityContext: {allowPrivilegeEscalation: false, capabilities: {drop: [ALL]}}`；
  - 注释说明：动态卷目录权限 0777（D-27），非 root 可直接写；不需要 fsGroup。

  Role 只有 leases、subjects namespace、emptyDir、无 mountPropagation、sidecar 版本固定、示例非 root）。
- 真实集群验收（架构师执行，K8s 1.28.15，镜像 `sha-<T-11 提交>`）：
  1. 两个 controller Pod 3/3 Ready 且在不同节点；Lease 被其中一个持有；provisioner 日志无 RBAC `forbidden`；
  2. 动态示例（clusterID / 父卷改为测试集群）：PVC 数秒内 Bound，PV 的 volumeHandle 为 `gfs:v1:subdir:<cluster>:csi-parent:pvc-…`；
     3 个非 root writer Pod 分布在 3 个节点同时写，各 Pod 读到全部 3 个文件且序号连续；Gluster 上目录权限 0777、有元数据；
  3. 删除示例（PVC）后 PV 被删除，目录出现在 `.glusterfs-csi/archive/`、元数据被删；
  4. 删除持有 Lease 的 controller Pod：另一副本在约 15s 内接手，期间新建的 PVC 最终 Bound；
  5. 把 StorageClass 换成 `onDelete: delete` 再走一遍创建/删除，目录被删除。
