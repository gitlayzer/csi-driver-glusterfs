## A 部分：超长卷名的派生子目录名（D-30）

### A.1 `pkg/volumeid`：新增 `SubdirName`

```go
// SubdirHashLength is the number of hexadecimal digits of the SHA-256 of a volume
// name that a derived subdirectory name ends with (D-30).
const SubdirHashLength = 16

// SubdirName returns the subdirectory name a subdir volume called name gets in
// volume of clusterID: the name itself when the encoded volume id fits into
// MaxLength, otherwise a derived name (D-30).
func SubdirName(clusterID, volume, name string) (string, error)
```

行为（严格按顺序）：
1. 依次用 `ValidateName` 校验 `clusterID`（字段名 `"cluster id"`）、`volume`（`"volume"`）、`name`（`"name"`），出错原样返回（已包裹 `ErrInvalid`）。
2. `budget` = `MaxLength` 减去 `gfs:v1:subdir:<clusterID>:<volume>:` 的字节数（即 `Prefix`、`Version`、`ModeSubdir`、`clusterID`、`volume`
   的长度之和再加 5 个冒号）。用现有常量计算，不要写死数字 14。
3. `len(name) <= budget` → 返回 `name`（K8s 的 `pvc-<uuid>` 永远走这里）。
4. `budget < SubdirHashLength+2` → 返回 `invalidf("invalid volume id: cluster id %q and volume %q leave %d bytes for the subdirectory, at least %d are needed", ...)`。
5. 否则返回 `name[:budget-SubdirHashLength-1] + "-" + hex.EncodeToString(sha256.Sum256([]byte(name)))[:SubdirHashLength]`（小写十六进制）。
   结果长度恰好等于 `budget`，所以 `Encode` 出来的 volume_id 恰好是 `MaxLength` 字节。

注释写清楚：派生名只由卷名决定，重复调用结果相同（幂等）；只用于 CreateVolume，其它 RPC 从 volume_id 里取子目录名；
不同长名的哈希前缀相同的概率可以忽略（64 位）。

### A.2 `pkg/driver/controller.go`：CreateVolume 使用派生名

- 现有的前置检查顺序不变：name 为空 → `InvalidArgument`；`ValidateName` → `InvalidArgument`；以 `.` 开头 → `InvalidArgument`；
  能力、容量、content source、mutable parameters、参数解析、cluster 查找，全部保持原样。
- cluster 查找之后、构造 `id` 之前：`subdir, err := volumeid.SubdirName(params.ClusterID, params.ParentVolume, name)`；出错返回
  `InvalidArgument`（`"cannot derive a directory name for volume %q: %v"`）。这一步在挂载父卷之前，失败时不得挂载。
- `subdir != name` 时记一条 `klog.InfoS("volume name does not fit into a volume id, using a derived directory name", "name", name, "subdir", subdir)`。
- `id.Subdir = subdir`。**之后所有目录与元数据操作（`readVolumeMeta`、`volumeDirExists`、`writeVolumeMeta`、`ensureVolumeDir`）以及
  涉及目录的错误信息都改用 `id.Subdir`**，不能再用 `name`。日志可以同时带 `name` 和 `subdir`。
- `volumeid.Encode` 失败的分支保留，作为防御性检查；把那行注释改为说明 SubdirName 之后不应再失败。
- 更新 `CreateVolume` 的文档注释：子目录名通常就是卷名，超长时按 D-30 派生。
- DeleteVolume、ValidateVolumeCapabilities 以及 Node 侧都不改：它们本来就从 volume_id 取子目录名。

### A.3 测试

`pkg/volumeid/volumeid_test.go` 新增表驱动的 `TestSubdirName`，至少覆盖：
- `pvc-<uuid>`（40 字符）在 `dev`/`csi-parent` 下原样返回；
- 长度恰好等于 `budget` 的名字原样返回；`budget+1` 的名字被派生，派生结果长度等于 `budget`、以 `-` 加 16 位小写十六进制结尾、
  用它 `Encode` 出的 volume_id 恰好 128 字节；
- 128 字符的名字（形如 sanity 的 `sanity-controller-create-maxlen-0123ABCD-4567EF01aaaa…`）的派生结果与**写死的期望字符串**相等
  （期望值用 `sha256sum` 独立算出后写进测试，不要在测试里调用被测函数自己的哈希逻辑去生成期望值）；
- 同一输入两次结果相同；两个前 120 个字符相同、末尾不同的长名得到不同结果；
- `budget` 等于 17 → `ErrInvalid`；等于 18 → 成功，结果是 1 个字符的前缀加 `-` 加哈希；clusterID 与 volume 很长、`budget` 为负 → `ErrInvalid`；
- `clusterID`、`volume`、`name` 为空或含非法字符 → `ErrInvalid`（`errors.Is`）。

`pkg/driver/controller_test.go` 新增：
- 128 字符卷名：CreateVolume 成功；返回的 volume_id 不超过 128 字节，`volume_context["subdir"]` 等于派生名；父卷里有派生名目录（0777）和
  `.glusterfs-csi/volumes/<派生名>.json`；**不存在**以完整卷名命名的目录；
- 同一个长名再调用一次 → 同一 volume_id；同一个长名换一个 `onDelete` → `AlreadyExists`（证明是按派生名查到的元数据）；
- 对返回的 volume_id 调 DeleteVolume → 派生名目录与元数据都被删除；
- 两个前 120 字符相同的长名 → 两个不同目录、两个不同 volume_id；
- 短名（`pvc-<uuid>`）的子目录名与卷名相同（如果已有用例已经断言了这一点，指出是哪个用例即可）；
- 配置中 clusterID 与父卷名都很长、剩余不足 18 字节时传长卷名 → `InvalidArgument`，且没有任何挂载调用、父卷里没有新文件。

## B 部分：csi-sanity 测试框架（D-31）

所有脚本用 bash，`set -euo pipefail`，通过 `shellcheck`；风格参照 `hack/verify-manifests.sh`（文件头注释说明用途和可用的环境变量）。
脚本只用 gluster 命令的退出码判断成败，**不解析任何 gluster 的人类可读输出**。所有外部命令都用参数数组调用，不拼命令字符串。

### B.1 `test/sanity/gluster.Dockerfile`（gluster 服务端）
- `ARG BASE_IMAGE=debian:trixie-slim`，`FROM ${BASE_IMAGE}`；`apt-get install -y --no-install-recommends glusterfs-server`，清理 apt 列表。
- `ENTRYPOINT ["/usr/sbin/glusterd", "-N", "--log-level=INFO"]`：`-N` 让 glusterd 留在前台，容器与它同生命周期。
- 文件头注释：只用于 csi-sanity，单节点、单 brick，不是生产镜像。

### B.2 `test/sanity/runner.Dockerfile`（驱动 + csi-sanity）
```dockerfile
ARG GO_IMAGE=golang:1.27
ARG DRIVER_IMAGE=glusterfs-csi:sanity
FROM ${GO_IMAGE} AS csi-sanity
ARG GOPROXY
ARG CSI_SANITY_VERSION=v5.6.0
RUN CGO_ENABLED=0 GOBIN=/out go install github.com/kubernetes-csi/csi-test/v5/cmd/csi-sanity@${CSI_SANITY_VERSION}

FROM ${DRIVER_IMAGE}
COPY --from=csi-sanity /out/csi-sanity /usr/local/bin/csi-sanity
COPY config.json parameters.yaml run-in-container.sh /sanity/
ENTRYPOINT ["/sanity/run-in-container.sh"]
```
注释说明：基础镜像就是发布用的驱动镜像，所以测的是真正发布的二进制（`/glusterfs-csi`）和镜像里的 glusterfs-client；
`GOPROXY` 只是为了让本地网络可以传入代理，默认不设。

### B.3 `test/sanity/config.json` 与 `test/sanity/parameters.yaml`
- `config.json`：`[{"clusterID": "sanity", "servers": ["gluster-server"]}]`（格式与 `deploy/kustomize/overlays/sample` 的配置一致，2 空格缩进）。
- `parameters.yaml`（StorageClass 参数，sanity 的 `--csi.testvolumeparameters`）：
  `clusterID: sanity`、`provisioningMode: subdir`、`parentVolume: csi-parent`、`onDelete: delete`。
  注释说明：用 `delete`，sanity 删除的卷不会留在父卷里，运行结束后可以检查父卷是否干净。

### B.4 `test/sanity/run-in-container.sh`（在 runner 容器内运行）
常量：`OUT=/out`、`SOCK=/csi/csi.sock`、`PARENT=/var/lib/glusterfs-csi/controller/sanity/csi-parent`、`STATE=/var/lib/glusterfs-csi/state`、
`MOUNT_DIR=/tmp/csi-mount`、`STAGING_DIR=/tmp/csi-staging`。脚本接受的参数全部原样追加到 csi-sanity 命令行末尾（便于 `--ginkgo.focus=...`）。

1. `mkdir -p /csi "$OUT" "$STATE" /var/log/glusterfs/csi`。
2. 后台启动驱动，参数顺序固定：
   `/glusterfs-csi --mode=all --endpoint=unix://$SOCK --nodeid=sanity-node --config=/sanity/config.json
   --controller-mount-dir=/var/lib/glusterfs-csi/controller --state-dir=$STATE --mount-log-dir=/var/log/glusterfs/csi --v=4`，
   stdout/stderr 写到 `$OUT/driver.log`。`--recovery-interval` 用默认值（与生产一致，恢复器在测试期间照常运行）。
3. 最多等 30s 直到 `$SOCK` 是 socket；超时则打印驱动日志最后 50 行并以 1 退出。
4. 运行 csi-sanity（失败不退出脚本，记下退出码 `rc`）：
   `csi-sanity --csi.endpoint=unix://$SOCK --csi.mountdir=$MOUNT_DIR --csi.stagingdir=$STAGING_DIR
   --csi.testvolumeparameters=/sanity/parameters.yaml --csi.testvolumesize=1073741824
   --ginkgo.junit-report=$OUT/junit.xml --ginkgo.no-color "$@"`。
5. 运行后检查（在停止驱动之前），每一项不满足都打印一行以 `LEFTOVER:` 或 `CHECK FAILED:` 开头的说明并把 `rc` 置 1：
   - `$PARENT` 是挂载点（看 `/proc/self/mountinfo` 第 5 列）；不是则 `CHECK FAILED: parent volume is not mounted, cannot check for leftovers`；
   - 是挂载点时：`$PARENT` 下除 `.glusterfs-csi` 外没有任何条目；`$PARENT/.glusterfs-csi/volumes` 与 `$PARENT/.glusterfs-csi/archive` 都为空；
   - `/proc/self/mountinfo` 中没有挂载点位于 `$MOUNT_DIR` 或 `$STAGING_DIR` 之下；
   - `$STATE` 下没有文件（每次 NodeUnstageVolume 都删除了自己的记录）；
   - `driver.log` 中没有 `panic:` 或 `fatal error:`。
6. 向驱动发 SIGTERM，最多等 30s；驱动的退出码必须为 0（超时或非 0 → `CHECK FAILED`，超时后发 SIGKILL）。
7. 驱动退出后 `/proc/self/mountinfo` 中不得再有文件系统类型为 `fuse.glusterfs` 的挂载（`CHECK FAILED: glusterfs mounts left after shutdown`）。
   注意 mountinfo 的文件系统类型在 ` - ` 分隔符之后的第一个字段。
8. 把 `/var/log/glusterfs/csi` 复制到 `$OUT/mount-logs`；`chmod -R a+rwX "$OUT"`（Linux CI 上产物属于 root，否则 runner 用户删不掉）。
9. 打印 `csi-sanity: PASS` 或 `csi-sanity: FAIL`，以 `rc` 退出。

### B.5 `hack/run-sanity.sh`（在宿主机上编排）
环境变量（都写进文件头注释）：
- `DOCKER`（默认 `docker`）；
- `GO_IMAGE`、`BASE_IMAGE`：设置了才作为 `--build-arg` 传给驱动镜像、gluster 镜像和 runner 镜像的构建（本地可以指向镜像加速器，脚本里**不写任何镜像源**）；
- `GOPROXY`：设置了才传给 runner 镜像的构建；
- `DRIVER_IMAGE`：设置了就直接用这个驱动镜像（例如 `ghcr.io/gitlayzer/glusterfs-csi:sha-xxxxxxx`），否则用仓库根目录的 `Dockerfile`
  构建 `glusterfs-csi:sanity`（单架构，`docker build`，带 `VERSION`/`GIT_COMMIT` build-arg，取值方式与 Makefile 一致）；
- `OUT_DIR`（默认 `_output/sanity`，脚本内转成绝对路径）；
- `KEEP=1`：结束后不删除容器、网络和 brick 卷，并打印它们的名字，便于排查。

流程：
1. 切到仓库根目录；清空并创建 `OUT_DIR`。
2. 构建三个镜像：驱动镜像（除非给了 `DRIVER_IMAGE`）、`glusterfs-csi-sanity-gluster:local`（`-f test/sanity/gluster.Dockerfile test/sanity`）、
   `glusterfs-csi-sanity-runner:local`（`-f test/sanity/runner.Dockerfile test/sanity`，`--build-arg DRIVER_IMAGE=...`）。
3. 资源名统一用前缀 `glusterfs-csi-sanity-${RUN_ID}`（`RUN_ID` 默认 `$$`）：网络 `<前缀>-net`、gluster 容器 `<前缀>-gluster`、
   runner 容器 `<前缀>-runner`。`trap` 在 EXIT 时清理：除非 `KEEP=1`，删除两个容器（`rm -f -v`，连同匿名 brick 卷）和网络；
   清理失败不得改变脚本的退出码。
4. `docker network create <前缀>-net`。
5. 启动 gluster 容器：`-d --privileged --name <前缀>-gluster --hostname gluster-server --network <前缀>-net --network-alias gluster-server
   --mount type=volume,dst=/bricks`（brick 需要支持 trusted xattr 的文件系统，所以放在 docker 卷上，不放在容器的 overlay 根文件系统上）。
6. 最多等 60s，直到 `docker exec <gluster> gluster --mode=script pool list` 成功。
7. `gluster --mode=script volume create csi-parent gluster-server:/bricks/csi-parent force`，然后 `volume start csi-parent`；
   再最多等 30s，直到 `gluster --mode=script volume status csi-parent` 成功。任何一步失败：打印 gluster 容器的日志并以 1 退出。
8. 运行 runner：`--privileged --network <前缀>-net --name <前缀>-runner -v "$OUT_DIR:/out"`（`KEEP` 不为 1 时加 `--rm`），
   把脚本自己的参数原样传给容器（即传给 csi-sanity）。记下退出码。
9. runner 失败时：`docker cp <gluster>:/var/log/glusterfs "$OUT_DIR/gluster-logs"`（失败不影响退出码）。
10. 最后一行打印结果与产物目录，以 runner 的退出码退出。

   `SubdirName` 在挂载之后才调用 —— 每一个都必须让测试失败。
2. 本地 `make sanity`（Docker Desktop，特权容器）：csi-sanity 0 失败；所有被跳过的用例都对应未声明的能力（GetCapacity、ListVolumes、
   快照、ControllerPublish、扩容、ModifyVolume、NodeGetStorageHealth 等）；运行后检查全部通过（父卷干净、无残留挂载与记录、驱动正常退出）。
3. CI 的 `CSI sanity` job 通过，产物里有 `junit.xml` 与 `driver.log`。
4. `KEEP=1` 时资源保留、默认时全部清理（`docker ps -a`、`docker network ls`、`docker volume ls` 无残留）。

## 不要做的事
- 不要把 csi-test 加进 `go.mod`，不要在 Go 测试里调用 sanity 包。
- 不要为了让 sanity 通过而跳过用例（`--ginkgo.skip`）或修改 A 部分以外的驱动代码。
- 不要在脚本或 Dockerfile 里写镜像加速器、代理地址或任何凭据。
- 不要提交 `_output/`。
